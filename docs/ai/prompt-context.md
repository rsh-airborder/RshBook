# 把提示词写成一份可复用的工作说明

很多提示词失败，并不是措辞不够“高级”，而是缺少人类同事默认知道的背景。与其反复追求一句万能咒语，不如把提示词写成一份短小、可复用的工作说明。

## 一份工作说明包含什么

一个稳定的提示词通常有五块：角色、目标、材料、约束和验收标准。它们不需要很长，但应当消除关键歧义。

```text
你是：一名帮助整理技术笔记的编辑。
目标：把下面的素材整理成一篇面向初学者的 Markdown 笔记。
材料：<粘贴原始资料>
约束：不编造来源；保留不确定处；中文；控制在 800 字内。
验收：包含标题、3 个小节、一个可执行清单和“仍待确认的问题”。
```

这比“帮我写篇笔记”更容易获得可用结果，也更容易发现结果哪里不合格。

## 先给上下文，再给动作

模型并不了解你的读者、代码库或偏好。把背景放在动作前面，能显著减少来回修正。背景可以是读者水平、文章用途、已有结论、禁止事项，或一个你喜欢的输出样例。

例如，要求“写得专业”很模糊；改成“读者会 Python，但不了解 LLM；避免数学推导；用一个 API 调用示例解释”就具体得多。

## 让它先提问，而不是直接猜

在素材不足时，加入一句：

> 如果缺少会影响结论的信息，先提出不超过三个澄清问题；不要自行补全事实。

这条约束特别适合方案、总结和编程任务。它把错误从最终输出提前到了可修正的提问阶段。

## 把常用提示词做成模块

不要保存一大段不可修改的提示词。把它拆成可以替换的模块：

- 固定模块：输出语言、事实边界、格式要求。
- 任务模块：本次要解释、比较或生成什么。
- 材料模块：文章、代码、会议记录或数据。
- 验收模块：长度、受众、必须出现的章节。

这样同一套工作说明可以用于读书笔记、项目复盘和教程初稿。

## 交付前的检查清单

1. 输入里是否给了必要事实，而不是让模型猜？
2. 是否写清了哪些内容不能编造？
3. 输出是否有可检查的结构？
4. 是否保留了人工判断和最终核对？

好的提示词不是更长，而是让下一步更确定。
