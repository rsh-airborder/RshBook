# 让 AI 帮你写代码前，先给它这 4 类上下文

AI 编程助手最容易犯的错，往往不是语法错误，而是在不了解项目边界时做出“看起来合理”的改动。想让它更像可靠的结对伙伴，先把上下文补齐。

## 1. 任务边界：改什么，不改什么

先用两三句话限定目标：

```text
目标：为文章页显示最后更新时间。
允许修改：VitePress 配置和主题样式。
不要修改：Markdown 内容、部署工作流和依赖版本。
```

这比“加一个更新时间”更能避免范围蔓延。

## 2. 现场证据：代码、报错和现状

贴出相关文件的最小片段、执行命令和完整错误。不要只转述“构建失败了”。如果已有类似页面或组件，也指出它的位置；项目内的成功案例比泛泛的最佳实践更有价值。

## 3. 项目规则：风格、测试与约束

告诉助手仓库的约定：包管理器、格式化方式、允许的依赖、必须运行的检查，以及不能碰的目录。这样它能把建议落到当前项目，而不是创造一套新架构。

## 4. 验收标准：怎样算完成

将“完成”写成可验证的条件：

- `npm run docs:build` 成功；
- AI 页面能看到“最后更新”；
- 首页不出现该字段；
- 没有未提交的生成文件。

验收标准不仅用于最后检查，也会反过来约束实现方案。

## 一个可直接复用的请求模板

```text
仓库背景：<技术栈与相关目录>
目标：<要完成的变化>
边界：<允许与禁止修改的内容>
现状：<代码片段、命令输出或报错>
验收：<可执行的检查>

请先说明你准备修改哪些文件和原因；确认后再给出改动。
```

## 小结

把上下文当作接口设计：输入越清楚，输出越容易验证。你仍然负责决定方向，AI 则负责加快明确范围内的实现。
