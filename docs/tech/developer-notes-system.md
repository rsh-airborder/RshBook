# 我的开发记录方法：让“以后再看”真的找得到

开发过程中最容易丢失的不是代码，而是当时为什么这样做、踩过什么坑、哪个命令真正有效。记录的目标不是积累更多文字，而是在需要时用几十秒找回一个决定。

## 先把记录分成三层

我会把信息分成收集箱、项目记录和可复用笔记。

- **收集箱**：还没整理的链接、截图、灵感，追求快。
- **项目记录**：当前项目的决定、命令、环境问题，追求上下文。
- **可复用笔记**：脱离具体项目后仍有价值的方法，追求可搜索与可阅读。

三层不必使用三套工具；即使都放在 Markdown 中，只要入口清楚也足够。

## 记录“触发条件”和“解决办法”

只写“修好了”没有价值。一个能复用的故障记录至少回答四个问题：

```text
现象：构建后资源路径 404
触发条件：部署到 GitHub Pages 的项目子路径
原因：站点基础路径仍是根路径
解决：设置 VitePress base 为 /仓库名/
验证：线上页面和静态资源均返回 200
```

这个格式让未来的你能够判断“这是不是同一个问题”。

## 给文件名稳定的语义

比起按日期堆文件，我更偏好按主题命名，例如 `github-pages-base-path.md`、`prompt-context.md`。日期可以放在正文或 Git 历史中；文件名应优先帮助搜索。

当一篇笔记变长时，用标题和链接拆分，而不是另起一个几乎同名的新文件。

## 每次记录只花两分钟

建立记录习惯的关键是降低门槛。任务结束时只写三行：做了什么、在哪里卡住、下次从哪里继续。之后若这个问题再次出现，再把它扩展成完整笔记。

这比要求自己“每次都写复盘”更容易坚持，也能让真正高频的问题自然浮现。

## 一个可复制的模板

```markdown
# 标题：一句话描述问题或方法

## 场景

## 结论

## 过程与命令

## 仍待确认

## 关联链接
```

## 小结

能找得到的记录，才是资产。先让输入足够轻，再让高价值内容慢慢沉淀到可复用的笔记库里。
