# 一个人维护项目时，最值得先建立的 5 个习惯

独立维护项目并不意味着什么都要自己做完，而是要让未来的自己能够快速理解、修改并继续推进。很多工程问题不是技术难，而是缺少一套低成本的日常习惯。

## 1. 每次改动只解决一个清楚的问题

一次提交最好能用一句话解释：修复一个错误、增加一个页面、调整一段样式。小改动容易检查、回滚和定位问题；当你几周后回看历史，也能迅速找到当时的意图。

如果发现需求牵涉多个方向，先列出拆分点，而不是用一个巨大提交把它们混在一起。

## 2. 把“能跑”变成一个固定命令

为项目保留最短的验证命令，例如：

```bash
npm run docs:build
```

每次提交前都运行它。验证不必一开始就很复杂；一个可靠的构建检查，已经能挡住大量路径错误、配置错误和语法错误。

## 3. 写下为什么，而不只写下做了什么

代码和配置告诉你“做了什么”，提交信息和短文档应该补上“为什么”。例如，VitePress 项目页为什么要设置 `/RshBook/` 基础路径？因为 GitHub Pages 的项目站点不部署在根域名。

当决定不是显而易见时，用一句注释或一个简短说明保存理由，能减少未来的重复思考。

## 4. 让生成物离开版本控制

依赖目录、构建产物、临时预览和本地缓存都应该放进 `.gitignore`。仓库应保存能重建结果的源文件，而不是把机器状态带给其他人或未来的自己。

判断标准很简单：删除这个文件后，能否通过安装依赖和运行构建重新得到它？如果可以，它大概率不该提交。

## 5. 为发布保留一个可追踪的出口

无论是网站、脚本还是服务，都要知道“这次改动是否真的上线”。对静态站点而言，GitHub Actions 的构建结果与在线地址就是出口；对其他项目，可能是测试报告、部署日志或版本号。

不要把“已经推送”误当作“用户已经能用”。最后验证一次线上结果，会让发布闭环。

## 一周实践清单

- 每天结束前把未完成想法写进 issue 或笔记；
- 每次改动保持在一个目的内；
- 提交前运行最短验证命令；
- 推送后看一次自动化结果；
- 周末删掉不再需要的临时分支和笔记草稿。

项目不需要一开始就有复杂流程。能被你稳定坚持的小习惯，才是最有效的工程系统。
